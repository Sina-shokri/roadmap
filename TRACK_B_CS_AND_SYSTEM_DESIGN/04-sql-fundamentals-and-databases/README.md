## 1️⃣ طراحی رابطه‌ای و نرمال‌سازی داده‌ها (Normalization)

نرمال‌سازی برای جلوگیری از تکرار داده‌ها (Redundancy) و ناهنجاری‌های بروزرسانی (Update Anomalies) انجام می‌شود:

- **فرم اول نرمال (1NF):** هر ستون باید حاوی مقدار اتمیک (تجزیه‌ناپذیر) باشد و ردیف‌ها ستون‌های تکراری با نام مشابه نداشته باشند.
- **فرم دوم نرمال (2NF):** باید در 1NF باشد و تمام ستون‌های غیرکلید وابستگی تابعی کامل به کلید اصلی داشته باشند (نه فقط به بخشی از یک کلید ترکیبی).
- **فرم سوم نرمال (3NF):** باید در 2NF باشد و هیچ ستون غیرکلیدی به ستون غیرکلید دیگر وابسته نباشد (حذف وابستگی تعدی/انتقالی).

> ⚖️ **تریدآف در دنیای واقعی:** در سیستم‌های عملیاتی (OLTP)، معمولاً دیتابیس در سطح 3NF نگه داشته می‌شود تا درج و آپدیت سریع و امن باشد. اما در سیستم‌های گزارش‌گیری و تحلیلی (OLAP / Data Warehouse)، گاهی عمداً به سمت Denormalization (غیرنرمال‌سازی کنترل‌شده) می‌رویم تا تعداد JOINها کاهش یابد.

## 2️⃣ انواع اتصال‌ها در SQL (SQL Joins Deep Dive)

فرض کنید دو جدول `users` (کاربران) و `orders` (سفارشات) داریم:

```
users: (id, name)               orders: (id, user_id, amount)
[1, 'Ali']                      [101, 1, 500]
[2, 'Reza']                     [102, 1, 300]
[3, 'Sara']                     [103, 2, 700]
                                [104, 4, 150] (سفارش کاربری که حذف شده!)
```

### ۱. اتصال درونی (`INNER JOIN`)
فقط ردیف‌هایی را برمی‌گرداند که در هر دو جدول مقدار متناظر داشته باشند (اشتراک):
```sql
SELECT u.name, o.id AS order_id, o.amount
FROM users u
INNER JOIN orders o ON u.id = o.user_id;
```
*نتیجه:* علی و رضا (سارا چون خریدی نداشته و سفارش ۱۰۴ چون کاربرش در جدول نیست حذف می‌شوند).

### ۲. اتصال چپ (`LEFT JOIN` / `LEFT OUTER JOIN`)
تمام رکوردهای جدول چپ (`users`) را می‌آورد، حتی اگر هیچ سفارشی در جدول راست نداشته باشند (در این صورت ستون‌های راست `NULL` می‌شوند):
```sql
SELECT u.name, COALESCE(o.amount, 0) AS amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;
```
*کاربرد تجاری:* **یافتن کاربرانی که تاکنون هیچ خریدی انجام نداده‌اند!**
```sql
SELECT u.id, u.name
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.id IS NULL; -- کاربرانی بدون سفارش
```

### ۳. اتصال راست (`RIGHT JOIN`)
تمام رکوردهای جدول راست (`orders`) را برمی‌گرداند؛ حتی اگر کاربری در جدول چپ برای آن وجود نداشته باشد.

### ۴. اتصال کامل (`FULL OUTER JOIN`)
اجتماع کامل هر دو جدول؛ چه کاربر سفارش داشته باشد چه نداشته باشد، و چه سفارش کاربری داشته باشد چه نداشته باشد.

### ۵. اتصال ضربی (`CROSS JOIN`)
ضرب دکارتی هر ردیف جدول اول در تمام ردیف‌های جدول دوم (تعداد خروجی: $N \times M$). کاربرد در تولید جداول زمانی، ماتریس قیمت‌ها یا ترکیب رنگ و سایز محصولات.

## 3️⃣ تفاوت حیاتی `WHERE` در برابر `HAVING`

- **`WHERE`:** ردیف‌ها را **قبل** از انجام گروه‌بندی و محاسبات تجمیعی فیلتر می‌کند.
- **`HAVING`:** گروه‌ها را **بعد** از محاسبه توابع تجمیعی (`COUNT`, `SUM`, `AVG`) فیلتر می‌کند.

```sql
-- سناریو: یافتن مشتریانی با حداقل ۳ سفارش که مجموع خریدهای تاییدشده‌شان بالای ۱۰ میلیون تومان است
SELECT 
    customer_id, 
    COUNT(id) AS total_orders, 
    SUM(total_amount) AS total_spent
FROM orders
WHERE status = 'CONFIRMED'              -- فیلتر روی تک‌تک ردیف‌ها قبل از تجمیع
GROUP BY customer_id
HAVING COUNT(id) >= 3 AND SUM(total_amount) > 10000000; -- فیلتر روی گروه‌ها بعد از تجمیع
```

## 4️⃣ توابع پیشرفته تحلیلی و پنجره‌ای (Window Functions)

توابع پنجره‌ای بدون اینکه ردیف‌ها را ادغام (Collapse) کنند، محاسبات تحلیلی را در طول یک پنجره از ردیف‌ها انجام می‌دهند.

### الف) رتبه‌بندی با `ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`:
```sql
-- سناریو: یافتن ۳ محصول پرفروش در هر دسته‌بندی کالا
WITH RankedProducts AS (
    SELECT 
        category_id,
        name,
        price,
        sold_count,
        ROW_NUMBER() OVER (
            PARTITION BY category_id 
            ORDER BY sold_count DESC
        ) AS rank_in_category
    FROM products
)
SELECT *
FROM RankedProducts
WHERE rank_in_category <= 3;
```

### تفاوت توابع رتبه‌بندی در نمرات مساوی:
اگر دو محصول فروش برابر داشته باشند:
- `ROW_NUMBER()`: به ترتیب ردیف اعداد ۱، ۲، ۳، ۴ را می‌دهد (همیشه یکتا).
- `RANK()`: رتبه‌های برابر می‌دهد و پرش می‌کند: ۱، ۲، ۲، ۴.
- `DENSE_RANK()`: رتبه‌های برابر می‌دهد بدون پرش: ۱، ۲، ۲، ۳.

### ب) مقایسه با ردیف قبلی و بعدی (`LAG` و `LEAD`):
```sql
-- مقایسه فروش هر ماه با ماه قبل و محاسبه رشد درصدی
SELECT 
    month,
    revenue,
    LAG(revenue, 1) OVER (ORDER BY month) AS prev_month_revenue,
    ROUND(
        (revenue - LAG(revenue, 1) OVER (ORDER BY month)) * 100.0 / LAG(revenue, 1) OVER (ORDER BY month), 2
    ) AS growth_percentage
FROM monthly_sales;
```

## 5️⃣ کالبدشکافی ایندکس‌ها و ساختار B-Tree در دیتابیس

وقتی جدولی ایندکس ندارد، دیتابیس باید تمام صفحات دیسک جدول را از ابتدا تا انتها بخواند (**Sequential Scan**) که زمان آن $O(n)$ است.

```
                    [ ریشه (Root Node) ]
                          [ 50 | 100 ]
                         /     |      \
               /─────────      |       ─────────\
    [ گره میانی ]         [ گره میانی ]         [ گره میانی ]
       [ 20 ]               [ 70 ]               [ 120 ]
       /    \               /    \               /     \
    [ برگ ] [ برگ ]      [ برگ ] [ برگ ]      [ برگ ] [ برگ ]
 (داده‌ها مرتب‌شده در برگ‌ها + اشاره‌گر دوطرفه بین برگ‌ها برای Range Queryها)
```

### چرا B-Tree؟
1. درخت B-Tree ساختاری کم‌ارتفاع و پهن (High Fanout) دارد؛ بنابراین با تنها **۳ یا ۴ بار خواندن از دیسک** می‌توان رکوردی را در میان میلیاردها سطر پیدا کرد ($O(\log n)$).
2. گره‌های برگ با پیوند زنجیره‌ای به یکدیگر متصل هستند که جستجوهای دامنه‌ای (`BETWEEN`, `>`, `<`) را فوق‌العاده پرسرعت می‌کند.

### قانون پیشوند چپ در ایندکس‌های ترکیبی (Composite Index):
اگر ایندکسی روی سه ستون بسازید:
```sql
CREATE INDEX idx_users_country_city_age ON users(country, city, age);
```
- جستجو روی `WHERE country = 'Iran' AND city = 'Tehran'` 👈 **از ایندکس استفاده می‌کند.**
- جستجو روی `WHERE country = 'Iran'` 👈 **از ایندکس استفاده می‌کند.**
- جستجو روی `WHERE city = 'Tehran'` 👈 **نمی‌تواند از ایندکس استفاده کند!** چون ستون اول (چپ‌ترین ستون) غایب است!

### چه زمانی ایندکس نسازیم؟
1. روی جدول‌هایی که نرخ نوشتن/درج (`INSERT/UPDATE`) بسیار بالاست و خواندن کم است (هر درج باید ایندکس‌ها را هم به‌روز کند).
2. روی ستون‌هایی با تنوع کم (Low Cardinality) مثل جنسیت (`gender`) یا وضعیت بولی (`is_active`).

## 6️⃣ ترنزکشن‌های ACID و سطوح ایزولاسیون

تراکنش باید چهار ویژگی حیاتی داشته باشد:
- **Atomicity (اتمیک بودن):** همه دستورات اجرا شوند یا هیچ‌کدام اعمال نشود.
- **Consistency (سازگاری):** داده‌ها قبل و بعد از تراکنش با تمام Constraints سازگار باشند.
- **Isolation (ایزولاسیون):** تراکنش‌های هم‌زمان نباید در نتایج یکدیگر تداخل ایجاد کنند.
- **Durability (ماندگاری):** پس از Commit، تغییرات حتی در صورت قطع ناگهانی برق سرور در دیسک حفظ شوند (به کمک WAL - Write-Ahead Logging).

### پدیده‌های ناهنجاری و جدول ایزولاسیون SQL:
| سطح ایزولاسیون | خواندن کثیف (Dirty Read) | خواندن غیرقابل تکرار (Non-repeatable Read) | خواندن شبح‌وار (Phantom Read) |
| :--- | :---: | :---: | :---: |
| **Read Uncommitted** | ❌ رخ می‌دهد | ❌ رخ می‌دهد | ❌ رخ می‌دهد |
| **Read Committed** *(پیش‌فرض Postgres)* | ✅ امن | ❌ رخ می‌دهد | ❌ رخ می‌دهد |
| **Repeatable Read** *(پیش‌فرض MySQL)* | ✅ امن | ✅ امن | ❌ رخ می‌دهد (یا جلوگیری با MVCC) |
| **Serializable** *(بالاترین سطح)* | ✅ امن | ✅ امن | ✅ امن |

- **Dirty Read:** تراکنش الف دیتایی را می‌خواند که تراکنش ب ویرایش کرده ولی هنوز Commit نکرده است.
- **Non-repeatable Read:** تراکنش الف یک ردیف را می‌خواند، تراکنش ب آن را تغییر داده و Commit می‌کند؛ تراکنش الف همان ردیف را دوباره می‌خواند و مقداری متفاوت می‌بیند!
- **Phantom Read:** تراکنش الف ردیف‌هایی را با شرطی می‌خواند؛ تراکنش ب ردیف جدیدی ثبت می‌کند که با شرط الف تطابق دارد؛ الف بار دوم ردیف جدید (شبح) را می‌بیند.

## 7️⃣ تحلیل و عیب‌یابی کوئری با `EXPLAIN ANALYZE`

برای اینکه بفهمید دیتابیس واقعاً چه کار می‌کند:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 45000 AND status = 'PENDING';
```

### خروجی را چگونه بخوانیم؟
- **`Seq Scan`:** اسکن کل جدول! اگر روی جدول چند میلیونی ببینید، یعنی **آژیر خطر!** باید ایندکس اضافه کنید.
- **`Index Scan`:** دیتابیس از درخت B-Tree برای رفتن مستقیم به ردیف مربوطه در دیسک استفاده کرده است (سریع).
- **`Index Only Scan`:** بهشت پرفورمنس! تمام اطلاعات مورد نیاز در خود درخت ایندکس بوده و دیتابیس حتی به جدول اصلی (Heap Table) سر نزده است.
- **`Execution Time`:** زمان واقعی اجرای کوئری به میلی‌ثانیه.

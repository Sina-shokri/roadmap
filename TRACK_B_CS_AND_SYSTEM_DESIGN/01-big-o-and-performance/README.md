## 1️⃣ مراتب رشد و مقایسه سرعت الگوریتم‌ها

جدول زیر مقایسه می‌کند که اگر اندازه ورودی ($n$) برابر با **۱,۰۰۰,۰۰۰** (یک میلیون رکورد) باشد، تعداد عملیات تقریبی چقدر خواهد بود:

| نماد Big-O | نام | تعداد عملیات تقریبی برای $n = 1,000,000$ | وضعیت پرفورمنس | مثال در جاوا |
| :--- | :--- | :--- | :--- | :--- |
| **$O(1)$** | ثابت (Constant) | ۱ عملیات | 🚀 فوق‌العاده | خواندن یک عنصر از آرایه با ایندکس یا `map.get(key)` در حالت میانگین |
| **$O(\log n)$** | لگاریتمی (Logarithmic) | ~ ۲۰ عملیات | ⚡ بسیار عالی | جستجوی دودویی (Binary Search) یا جستجو در `TreeSet` |
| **$O(n)$** | خطی (Linear) | ۱,۰۰۰,۰۰۰ عملیات | ✅ خوب و قابل قبول | پیمایش ساده یک لیست یا حلقه `for` تک |
| **$O(n \log n)$** | خطی-لگاریتمی | ~ ۲۰,۰۰۰,۰۰۰ عملیات | 🆗 مناسب برای سورت | الگوریتم‌های مرتب‌سازی بهینه مثل Merge Sort و Quick Sort (`Arrays.sort()`) |
| **$O(n^2)$** | درجه دو (Quadratic) | ۱,۰۰۰,۰۰۰,۰۰۰,۰۰۰ عملیات | 🛑 فاجعه در دیتاهای بالا | دو حلقه تودرتو (Nested Loops) روی داده‌های بزرگ |
| **$O(2^n)$** | نمایی (Exponential) | غیرقابل محاسبه در کائنات! | 💥 غیرعملیاتی | تولید زیرمجموعه‌ها با بازگشتی غیربهینه |

## 2️⃣ ردپای حافظه در جاوا (Memory Footprint: Stack vs Heap)

یک برنامه‌نویس جونیور فکر می‌کند ذخیره ۱ میلیون عدد `int` با ذخیره ۱ میلیون `Integer` تفاوتی ندارد، اما در سطح JVM تفاوت وحشتناک است:

```
[ حافظه Stack ]
- بسیار سریع
- متغیرهای Primitive مستقیماً ذخیره می‌شوند (int x = 10; فقط ۴ بایت)
- متغیرهای محلی متدها و رفرنس‌های اشاره‌گر
- با خروج از متد، حافظه بلافاصله آزاد می‌شود (بدون نیاز به GC)

[ حافظه Heap ]
- اشیاء (Objects) با کلمه کلیدی new در اینجا ساخته می‌شوند
- سرور باید Object Header (۱۲ تا ۱۶ بایت)، متغیرهای شیء و Padding (ضریب ۸ بایت) را ذخیره کند
- Garbage Collector (GC) باید پیوسته هیپ را اسکن کند تا حافظه آزاد شود
```

### مقایسه واقعی مصرف حافظه برای ۱ میلیون عدد:
- **`int[] array = new int[1_000_000];`**
  - محاسبات: $1,000,000 \times 4 \text{ bytes} \approx \mathbf{4 \text{ MB}}$ رم!
- **`List<Integer> list = new ArrayList<>(1_000_000);`**
  - محاسبات: آرایه‌ای از ۱ میلیون رفرنس اشاره‌گر (۸ بایت در سیستم ۶۴ بیتی یا ۴ بایت با Compressed OOPs) + ۱ میلیون شیء مجزای `Integer` در هیپ که هرکدام حدود ۱۶ تا ۲۴ بایت فضا می‌گیرند!
  - جمع کل: حدود **$\mathbf{24 \text{ to } 32 \text{ MB}}$** (یعنی ۶ تا ۸ برابر مصرف رم بیشتر!).

## 3️⃣ نمونه تحلیل کد در عمل

### سناریو ۱: کد با مرتبه $O(n^2)$ (بد)
```java
// یافتن اینکه آیا دو عنصر مساوی در آرایه وجود دارد یا نه
public boolean hasDuplicateSlow(int[] nums) {
    for (int i = 0; i < nums.length; i++) {
        for (int j = i + 1; j < nums.length; j++) {
            if (nums[i] == nums[j]) return true;
        }
    }
    return false;
}
```
*تحلیل:* برای آرایه ۱۰۰,۰۰۰ عددی، حدود ۵ میلیارد مقایسه انجام می‌شود و سیستم چند ثانیه فریز خواهد شد!

### سناریو ۲: بهینه‌سازی به $O(n)$ با استفاده از فضا (خوب)
```java
public boolean hasDuplicateFast(int[] nums) {
    Set<Integer> seen = new HashSet<>();
    for (int num : nums) {
        if (!seen.add(num)) {
            return true;
        }
    }
    return false;
}
```
*تحلیل:* زمان اجرا به **$O(n)$** کاهش می‌یابد (در کمتر از ۱۰ میلی‌ثانیه برای ۱۰۰,۰۰۰ عدد) به قیمت مصرف کمی فضای کمکی (**Space Complexity: $O(n)$**). این همان مفهوم بده‌بستان زمان و فضا (Time-Space Tradeoff) است.

## ❓ سوالات مصاحبه و تمرین‌های فکری
1. **چرا پیچیدگی زمانی درج عنصر در انتهای `ArrayList` جاوا به صورت Amortized $O(1)$ بیان می‌شود؟**
   - *پاسخ:* چون در بیشتر مواقع فقط یک درج ساده در خانه بعدی آرایه است ($O(1)$). تنها زمانی که ظرفیت پر شود، آرایه‌ای جدید با اندازه ۱.۵ برابر ساخته شده و کل عناصر کپی می‌شوند ($O(n)$). با سرشکن شدن هزینه کپی بین هزاران درج معمولی، میانگین هزینه همچنان $O(1)$ باقی می‌ماند.
2. **کدامیک برای نگهداری سشن‌های کاربران بهینه‌تر است: آرایه یا هشت‌مپ؟**
   - با توجه به اینکه شناسه‌ها تصادفی و بزرگ هستند (مثلاً UUID)، جستجو در آرایه $O(n)$ است در حالی که در هش‌مپ $O(1)$ است.
